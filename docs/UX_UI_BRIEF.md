# บรีฟเริ่มออกแบบ UX/UI — Tire Inspection

วันที่ตรวจสถานะ: 10 พฤศจิกายน 2026

## 1. งานของ session ที่รับต่อ

ออกแบบขั้นตอนใช้งานและหน้าจอของระบบตรวจสภาพหน้ายางสำหรับทดลองหน้างาน เริ่มจากการนำเข้าภาพบน Windows และเตรียมให้เปลี่ยนเป็นกล้องบน Pi ภายหลัง ผู้ใช้ต้องการตรวจแบบก่อนพัฒนา ไม่ได้อนุมัติ framework, API, ฐานข้อมูล หรือรูปแบบติดตั้ง UI แล้ว

ให้เริ่มด้วย user flow, wireframe และรายการสถานะหน้าจอ ไม่ฝึกโมเดล ไม่เปลี่ยน threshold/ป้ายข้อมูล และไม่สร้างระบบส่วนที่ยังต้องตัดสินใจโดยอนุมานเอง

**workspace ที่ทำงานจริง:** `03-software-ux/tire-inspection/` เปิดโฟลเดอร์นี้ใน VS Code โปรแกรมไม่พึ่ง round2 ขณะรัน ส่วน round2 เป็นประวัติงานวิจัย ไม่ย้ายหรือลบ

## 3. สิ่งที่ยืนยันแล้ว

- ผู้ใช้พอใจโมเดลปัจจุบัน ให้ใช้เป็น baseline ทดลองหน้างาน แล้วเก็บผลปรับปรุงภายหลัง ไม่เปิดประเด็นฝึกใหม่เป็นเงื่อนไขกีดขวางการออกแบบ UI
- ใช้ YOLO11n-cls; release `round2-baseline-2026-11-10` มี .pt และ .onnx ตรวจ hash ตรงต้นทาง
- Windows .venv ติดตั้งแล้ว ทดสอบภาพเดี่ยว หลายภาพ/JSON และผล PT/ONNX สามตัวอย่างผ่าน เป็นการตรวจระบบ ไม่ใช่ความแม่นยำอิสระ
- ยังไม่มี Pi พร้อมทดสอบ ไม่มี camera integration, UI, API หรือระบบบันทึกประวัติสำเร็จรูป
- เป้าหมายฮาร์ดแวร์: Raspberry Pi 4 และ Camera Module 3; เครื่องถ่วงล้อ Mactech F-953 ใช้หมุนยาง กล้องใช้ขาตั้งแยก
- Owner เคยแจ้งประมาณหนึ่งรอบต่อ8วินาที ไม่ใช่ค่าที่โปรแกรมวัดได้หรือข้อกำหนดจับเวลาอัตโนมัติที่ยืนยันแล้ว
- ยังไม่มีหลักฐานว่าโปรแกรมสั่งหมุน/หยุดเครื่องถ่วงได้ ปุ่มเริ่มตรวจต้องหมายถึงเริ่มกระบวนการตรวจในโปรแกรม ไม่สื่อว่าควบคุมเครื่องถ่วง

### นิยามตาม Owner

| ผล | ความหมายที่ใช้ในหน้าจอ |
|---|---|
| Normal — สภาพปกติ | ลายดอกยางยังชัดเจน สึกค่อนข้างสม่ำเสมอ ไม่พบความเสียหายเด่นชัดจากภาพ |
| Warning — ควรตรวจสอบเพิ่มเติม | ภาพไม่ชัด สภาพก้ำกึ่ง หรือพบลักษณะที่น่าสงสัยแต่ยังตัดสินไม่ได้แน่นอน |
| Abnormal — ผิดปกติหรือเสียหาย | เห็นการสึกมาก ดอกยางโล้น รอยฉีก หรือความเสียหายที่มองเห็นได้ชัดเจน |

ไม่เพิ่มคำรับรองวัดความลึกเป็นมิลลิเมตร อายุคงเหลือ ตำแหน่งตำหนิ หรือความปลอดภัยในการขับขี่ เพราะโมเดลยังไม่ได้ส่งผลเหล่านี้

## 4. การตัดสินใจล่าสุดจากผู้ใช้ — 10 พฤศจิกายน 2026

1. **รองรับทั้งสองแบบ:** เบราว์เซอร์บนคอมพิวเตอร์/โน้ตบุ๊ก และจอสัมผัสที่ต่อกับ Pi
2. **ผู้ใช้หลักช่วงทดลองคือทีมวิจัย 3R:** เป็นผู้ดำเนินการและบันทึกผล

แนวทางสำหรับร่างแบบ:
- ใช้ขั้นตอนและความหมายข้อมูลเดียวกันทั้งสองรูปแบบ พร้อมแสดง wireframe สำหรับคอมพิวเตอร์และจอสัมผัส
- จอสัมผัสต้องกดใช้งานได้สะดวก ไม่พึ่ง hover หรือเมาส์เพียงอย่างเดียว; ขนาดและความละเอียดจอจริงยังไม่ทราบ ให้ระบุขนาดที่ใช้ร่างเป็นสมมติฐานเพื่อให้ผู้ใช้ตรวจ
- ให้ทีม3Rเริ่มรอบตรวจ ตรวจภาพ ดูผล และบันทึกข้อมูลได้ครบใน flow หลัก ไม่จำเป็นต้องสร้างบัญชี/สิทธิ์สำหรับช่างแยกโดยอัตโนมัติ
- ผู้บันทึกข้อมูลกับผู้ยืนยันสภาพยางอาจเป็นคนละคน การที่3Rกรอกข้อมูลไม่ได้แปลว่าเป็นผลช่างหรือ ground truth ที่ยืนยันแล้ว ต้องแยกแหล่งที่มาของผลตรวจ และเว้นสถานะยังไม่ยืนยันได้
- รองรับสองหน้าจอไม่ได้แปลว่าอนุมัติให้ใช้งานพร้อมกันผ่านเครือข่ายหรือบริการcloud รูปแบบเชื่อมต่อและframeworkยังต้องตกลงก่อนimplementation

เรื่องที่จะถามเมื่อถึงขั้นเกี่ยวข้อง ไม่ต้องถามทั้งหมดก่อนร่าง flow:
- รูปแบบรหัสยาง/รอบตรวจและผู้มีหน้าที่ยืนยันผลช่าง
- วิธีรับรองความครบวง จำนวน/ตำแหน่งภาพ และการถ่ายซ้ำ ไม่กำหนด3–8ภาพเป็นเกณฑ์ผ่านเอง
- รูปแบบเก็บประวัติ/ระยะเวลาเก็บ/ส่งออก และความต้องการหลายผู้ใช้หรือเครือข่าย
- framework, API และ deployment ให้ตัดสินใจก่อนเริ่ม implementation ไม่จำเป็นต่อ wireframe แรก

## 5. ขอบเขตการออกแบบรอบแรก (ข้อเสนอให้ผู้ใช้ตรวจ)

### A. เริ่มรอบตรวจ
แสดงแหล่งภาพที่ใช้งานได้จริง เริ่มจากไฟล์บนเครื่อง พื้นที่กล้องเป็น future state ที่ระบุชัด ไม่ทำเสมือนต่อกล้องแล้ว ระบุรหัสยาง/รอบตรวจตามรูปแบบที่จะตกลง และแยกรอบใหม่จากการเปิดประวัติ

### B. นำเข้าและตรวจรายการภาพ
แสดงภาพย่อ เปิดภาพใหญ่ได้ เห็นจำนวนภาพที่เลือก/อ่านได้/ผิดพลาดและเหตุผล ก่อนวิเคราะห์ให้ผู้ใช้ตรวจรายการ ไม่ทิ้งภาพที่อ่านไม่ได้เงียบ ๆ การลบออกจากรอบไม่ควรสื่อว่าลบไฟล์ต้นฉบับ

### C. กำลังวิเคราะห์
แสดงสถานะตามจำนวนที่ระบบรายงานจริง ออกแบบการวิเคราะห์ไม่สำเร็จและลองใหม่ ไม่สร้างเปอร์เซ็นต์หรือเวลาคงเหลือปลอม โค้ดเดิมยังไม่มี API progress/cancel ต้องทำ mock และระบุงาน backend ที่ต้องเพิ่ม

### D. ดูผล
แสดงผลรายภาพ พร้อมภาพและคะแนนสามคลาสในส่วนรายละเอียด ผลหลักใช้ผลหลังใช้กฎเดิม แยกจากผลคะแนนสูงสุด ไม่คำนวณกฎใหม่ใน UI

ผลรวมใช้ข้อความ **“ผลรวมจากภาพที่นำเข้า”** ตราบใดที่ยังไม่ยืนยัน coverage ไม่เรียก “ตรวจครบ360°แล้ว” จากจำนวนภาพหรือ overall_condition เพียงอย่างเดียว

คะแนนโมเดลไม่ใช่เปอร์เซ็นต์ความแม่นยำ ไม่แสดงคะแนน99.9%เป็นการรับรองว่าผลถูกต้อง99.9% ใช้ข้อความ/ไอคอนร่วมกับสี ไม่ใช้สีอย่างเดียว

### E. ผลตรวจของช่างและประวัติ
เสนอแบบบันทึกผลช่าง เหตุผล ความเห็นต่างจากAI และบริบทการถ่าย แยกจากผลAIดั้งเดิม ไม่เลือกผลช่างอัตโนมัติตามโมเดล ออกแบบสถานะยังไม่ตรวจ/ยังไม่บันทึก/บันทึกไม่สำเร็จ/บันทึกแล้วให้ชัด ประวัติและการบันทึกเป็นงานที่ยังต้องพัฒนา ไม่ใช่ของที่พร้อมแล้ว

## 6. สถานะที่ wireframe ต้องครอบคลุม

| ประเภท | ตัวอย่าง |
|---|---|
| ขั้นตอน | ยังไม่มีภาพ, พร้อมวิเคราะห์, กำลังวิเคราะห์, วิเคราะห์เสร็จ |
| ข้อมูลไม่ครบ | ภาพบางภาพหาย/อ่านไม่ได้, ยังไม่ยืนยันว่าเป็นยางเดียวกัน, ยังไม่ยืนยันความครบวง |
| ระบบผิดพลาด | โหลดโมเดลไม่ได้, คลาสไม่ตรง, วิเคราะห์ล้มเหลว, บันทึกไม่ได้ |
| ผลโมเดล | Normal, Warning, Abnormal |
| ผลช่าง | ยังไม่ตรวจ, ตรวจแล้วเห็นตรง/ต่างจากAI โดยเก็บค่าจริงแยกกัน |

**Warning ไม่ใช่ error ของระบบ** ภาพเปิดไม่ได้ไม่ถูกเปลี่ยนเป็น Warning/Normal โดยUI และการไม่มีผลยังไม่ใช่ Normal

## 7. การเชื่อมข้อมูลที่มีจริง

โค้ดปัจจุบัน: [predict.py](../inference/predict.py), [inference_engine.py](../inference/inference_engine.py) เป็น CLI/Python functions ยังไม่มี HTTP API ห้ามถือว่า frontend เปิดไฟล์จาก path Windows ได้โดยตรงทุกสถาปัตยกรรม ต้องออกแบบ adapter/การส่งภาพในขั้น implementation

| JSON ปัจจุบัน | ความหมาย/แนวทางแสดง |
|---|---|
| total_views | จำนวนภาพที่โปรแกรมประมวลผล ไม่ใช่จำนวนมุมที่รับรองครบวง |
| overall_condition | ผลรวมจากภาพที่ส่งเข้า ตาม maximum severity |
| normal_views_count / warning_views_count / abnormal_views_count | จำนวนผลรายคลาส |
| views[].filename / image | ชื่อและpathไฟล์; UIควรแสดงชื่อที่อ่านง่าย ไม่เปิดเผยpathเครื่องเป็นข้อมูลหลัก |
| views[].scores | คะแนนสามคลาส ปัจจุบันปัด4ตำแหน่ง |
| views[].argmax_prediction | คลาสคะแนนสูงสุด เก็บไว้ในรายละเอียด |
| views[].safety_prediction | ผลหลังthresholdเดิม ใช้เป็นผลหลักรายภาพ |
| views[].reason | คำอธิบายthreshold ไม่ใช่ตำแหน่ง/สาเหตุความเสียหาย |
| total_latency_ms / avg_latency_ms | เวลารวมการเรียกpredict ไม่ใช่เวลาตั้งแต่กล้องจนบันทึกเสร็จ |

กฎเดิม: Abnormal ≥0.25 ก่อน จากนั้น Warning ≥0.35 มิฉะนั้น Normal; รวมหลายภาพโดยเลือกผลรุนแรงสุด ไม่เพิ่มปุ่มปรับthresholdในหน้าจอใช้งานโดยไม่ได้ตกลง

ตัวอย่างJSON: [mixed-images-plumbing-only.json](../outputs/windows-check-2026-11-10/mixed-images-plumbing-only.json) **สามภาพนี้เป็นคนละตัวอย่างเพื่อทดสอบโค้ด ไม่ใช่ยางเส้นเดียว** ใช้ดูschemaได้ แต่ห้ามใช้เป็นหลักฐานตรวจยางจริงครบวงหรือประวัติหน้างานจริง

ข้อมูลที่ยังต้องเพิ่มใน adapter/storage (ข้อเสนอ ไม่ใช่schemaอนุมัติแล้ว): session_id, tire_id, view_id/ตำแหน่ง, เวลา, source_type, model_version/hash, policy_version, expected/received/failed images, coverage_status, ผลช่าง/เหตุผล และsave_status ดู [แบบบันทึก](../data/field-tests/template.csv)

## 8. ข้อจำกัด backend ที่กระทบ UX

1. โค้ดยังไม่ปฏิเสธโมเดลชื่อคลาสผิด อาจคืนNormalเมื่อคะแนนคลาสยางไม่มี ต้องมีbackend validationก่อนปล่อยUIใช้งานจริง
2. inputแบบcommaข้ามไฟล์หายเงียบ ๆ ต้องแก้backendให้รายงานก่อนถือว่ารายการครบ
3. aggregateรับภาพเดียวแล้วรวมผลได้ ไม่มีการตรวจตัวตนยาง/coverage ต้องออกแบบข้อความตามขอบเขตจริง
4. ไม่มีระบบบันทึกรอบตรวจ/ผลช่าง/ประวัติในตัว มีเพียงexport JSON
5. ONNXผ่านการทดลองWindows แต่scriptsยังพึ่งtorch/ultralytics ยังไม่ใช่ตัวรันPiแบบติดตั้งแค่ONNX Runtime

ออกแบบstateเหล่านี้ด้วยmockได้ แต่ห้ามอ้างว่าbackendรองรับแล้ว หรือแก้กฎโมเดลแทนการแก้backend

## 9. ผลส่งมอบที่คาดหวังจาก session UX/UI

1. สรุปคำตอบผู้ใช้และรายการเรื่องที่ยังไม่ตกลง
2. User flow ตั้งแต่เริ่มรอบตรวจถึงบันทึกผล พร้อมเส้นทางผิดพลาด
3. Wireframe หน้าหลักและสถานะสำคัญ โดยยังไม่ผูกframework
4. ตารางหน้าจอ → ข้อมูลที่ใช้ → มีแล้ว/ต้องเพิ่ม → ผู้รับผิดชอบ
5. Prototype สำหรับผู้ใช้ตรวจ โดยติดป้ายข้อมูลจำลองให้ชัด ไม่บันทึกทับผลวิจัย
6. หลังผู้ใช้ตรวจแบบ จึงเสนอเทคโนโลยีและแผนเชื่อมbackend ไม่ถือว่าบรีฟนี้อนุมัติimplementationทั้งหมด

เกณฑ์ตรวจแบบ: เห็นผลรายภาพ/ผลรวมต่างกันชัด, แยกAI/ช่าง, ไม่ใช้Warningแทนerror, ไม่สรุปครบวงอัตโนมัติ, ไม่กล่าวอ้างคะแนนเป็นaccuracy, มีempty/loading/error/save states และระบุงานbackendที่ยังขาด

## 10. ขอบเขตไฟล์สำหรับ session ถัดไป

เก็บงานออกแบบใน `ui/design/` (สร้างเมื่อเริ่มงาน) และเอกสารประกอบใน `docs/` อัปเดตSTATUSเมื่อจบงาน ห้ามแก้ models/, release policy, ข้อมูลฝึกในround2 หรือผลทดสอบเดิมเพื่อให้หน้าจอดูสมบูรณ์ ไม่เลือกcloud/database/บริการเสียเงินโดยไม่มีคำตอบผู้ใช้

เริ่ม session ได้ด้วยข้อความ: “อ่าน docs/UX_UI_BRIEF.md, PROJECT.md, STATUS.md และคำตอบผู้ใช้ล่าสุด เริ่มร่างuser flowและwireframeก่อน ยังไม่เลือกframeworkหรือแก้โมเดล ถ้าต้องตัดสินใจเพิ่มให้ถามผู้ใช้”
